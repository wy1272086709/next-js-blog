# 项目代码优化总结

## 1. 优化目标

本轮优化主要解决三个问题：

1. 公开文章页面每次访问都会重复查询数据库，首屏响应慢，服务器压力较大。
2. 文章正文、登录状态、点赞、Redis 和浏览量更新耦合在同一次服务端渲染中，任何一个依赖变慢都会拖慢整个页面。
3. 点赞链路依赖 Redis，Redis 断线重连时接口长时间不返回；CSRF token 不同步时还会返回 403。

整体思路是：公开内容尽量缓存，用户数据独立请求，数据库写操作不依赖缓存服务成功。

## 2. 公开文章页面改为 ISR

涉及代码：

- `app/[locale]/posts/page.tsx`
- `app/[locale]/posts/[id]/page.tsx`
- `lib/data/public-posts.ts`
- `lib/supabase/public.ts`

文章列表和文章详情设置了 300 秒重新验证时间。第一次生成页面后，后续访问可以直接复用 Next.js 缓存，不需要每次都重新执行完整的数据库查询和服务端渲染。

详情页使用按需生成，不在构建阶段枚举所有文章 ID。这样文章数量增加时，不会让构建时间线性增长。

为什么这样做：

- 已发布文章是公开数据，不应该因为访问者不同而生成不同正文。
- 文章允许短时间内存在缓存，5 分钟是当前项目在实时性和性能之间的折中。
- Dashboard 等用户私有页面仍然保持动态 SSR，避免把某个用户的数据缓存给其他用户。

## 3. 建立独立的公共数据查询层

公开文章查询不再使用读取 Cookie 和登录 Session 的 Supabase Client，而是使用无用户状态的公共 Client。查询层只读取已发布内容，并通过 Next.js 数据缓存复用结果。

为什么这样做：

- 在公开页面读取 Cookie 会让 Next.js 把页面视为请求相关内容，失去静态生成和共享缓存能力。
- 页面组件只负责展示，数据库查询规则集中在数据层，更容易统一缓存时间、字段和错误处理。
- 公共 Client 不持久化 Session，可以明确区分公开数据和用户私有数据的安全边界。

## 4. 将动态交互从正文渲染中拆出

文章详情页不再在服务端渲染阶段处理以下逻辑：

- 查询当前登录用户；
- 查询当前用户是否点赞；
- 读取 Redis 点赞缓存；
- 更新文章浏览量；
- 初始化 CSRF token。

点赞状态在 `LikeButton` 挂载后通过 `/api/posts/[id]/like` 获取，评论继续由客户端组件处理。正文因此可以作为公共页面缓存，而点赞等用户状态仍然保持实时。

浏览量原先使用“读取旧值再加一”的方式更新，并发访问时可能丢失计数。本轮先移除了渲染过程中的写操作。后续应通过独立接口和 PostgreSQL 原子更新实现浏览量统计。

为什么这样做：

- 页面渲染应该尽量是只读过程，避免刷新页面就触发隐式写操作。
- Redis、认证或评论服务异常时，不应导致文章正文也无法打开。
- 公共正文和个性化状态分开后，各自可以采用合适的缓存策略。

## 5. 修复点赞超时和数据一致性

涉及代码：

- `app/api/posts/[id]/like/route.ts`
- `hooks/use-like-mutation.ts`

点赞 API 已从主链路移除 Redis，直接以 Supabase 的 `post_likes` 表作为事实来源：

1. 客户端提交明确的目标点赞状态，避免服务端先查询一次当前状态；
2. 用户鉴权和当前点赞计数并行执行；
3. 根据目标状态插入或删除点赞记录，并修正返回计数；
4. GET 请求并行查询总数和当前用户状态。

原实现虽然有 Redis 异常降级，但每次 `get` 或 `set` 都可能先经历多轮连接重试。一次点赞又串行执行多次 Redis 操作，因此 Redis 出现 `Socket closed unexpectedly` 时，前端会长期停留在加载状态。

为什么移除而不是继续增加超时：

- 点赞是必须准确完成的用户写操作，缓存不应成为写入数据库之前的阻塞依赖。
- 当前查询规模下，按 `post_id`、`user_id` 建立索引后的数据库查询足够直接可靠。
- 原缓存计数通过内存中的旧值加减，遇到并发请求或缓存过期时可能产生计数漂移。

如果以后点赞访问量明显增加，可以重新引入 Redis，但应采用“数据库写入成功后异步失效缓存”的方式，Redis 失败不能影响接口返回。

## 6. 修复 CSRF token 不同步

涉及代码：

- `app/api/csrf/route.ts`
- `hooks/use-like-mutation.ts`
- `app/[locale]/layout.tsx`

CSRF 初始化接口以前每次请求都会生成新 token。页面出现并发初始化请求时，Supabase Session 中的 token 和浏览器 Cookie 可能分别保留不同版本，最终导致 `Invalid CSRF token`。

现在接口优先复用 Cookie 中已有的 token。客户端共享初始化请求，并把同一个 token 放入 `X-CSRF-Token` Header；中间件直接比较 Header 与 Cookie，不再读取请求体或访问 Supabase Auth。

同时删除了 Locale Layout 服务端请求自身 `/api/csrf` 的逻辑。客户端已有统一的 CSRF Provider，服务端自请求既重复，也会在构建阶段等待一个尚未启动的本地服务。

## 7. API 路由与构建配置优化

`proxy.ts` 现在优先识别 `/api/*`，API 不再经过页面国际化重定向，避免接口在 locale 路径之间重定向或循环。历史上的 `/{locale}/api/*` 地址仍保留兼容重写。

`next.config.mjs` 显式指定 Turbopack 项目根目录，避免 monorepo 或上级目录中的锁文件让构建工具错误推断 workspace root。

## 8. 当前效果

此前的生产环境测量结果：

| 页面 | 首次请求 | 缓存后平均响应 | 缓存状态 |
| --- | ---: | ---: | --- |
| 文章列表 | 98.5 ms | 7.2 ms | HIT |
| 文章详情 | 312.4 ms | 6.7 ms | HIT |

文章详情第一次按需生成仍需要查询数据库，之后会复用 ISR 页面缓存。详情页首个访问者的耗时会受到数据库和数据缓存状态影响，不能只看热缓存数据。

点赞接口现在不再等待 Redis，因此 Redis 断线不会阻塞点赞。点赞结果和计数统一来自数据库，逻辑也比原先更容易排查。

## 9. 当前限制与后续建议

1. 将文章新增、编辑和删除统一收口到服务端接口，成功后调用 `revalidateTag`，避免固定等待 5 分钟。
2. 使用 PostgreSQL 函数实现浏览量原子递增，并增加防刷或去重策略。
3. 统一历史上的 `likes` 和 `post_likes` 表，减少模型混淆。
4. 评论列表和评论点赞可改为聚合 API，避免客户端读取过多明细数据。
5. 修复项目现有 TypeScript 错误，并安装 ESLint；当前构建配置会忽略类型错误，这会掩盖潜在问题。
6. 在真实部署环境继续监控 Supabase 请求耗时、点赞接口错误率和 ISR 缓存命中率，再决定是否需要重新引入 Redis。

更详细的缓存设计、测试方法和性能数据见 `docs/rendering-performance-design.md`。
